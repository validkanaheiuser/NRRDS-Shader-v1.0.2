**Critical design note:** `-nostdlib++` is intentionally used (NOT `-static-libstdc++`) for the Zygisk module. ### 5. Anomalies

#### A1 — TLS private key committed to repository
- **File:** `server/server.key`
- **Severity:** HIGH
- The TLS server private key is committed alongside `server/server.crt`. Any party with read access to the repository history can extract the private key and perform MiTM attacks against any server deployment using this certificate.

#### A2 — Windows DLL committed to repo
- **File:** `server/opus.dll`
- **Classification:** Unexpected binary
- This is a Windows shared library (`.dll`) inside the Python/FastAPI server directory of an Android project. No Python or Node.js code in the repo references `opus.dll` by name. It may be a developer convenience artifact for running the server on Windows.

#### A3 — Compiled server zip committed
- **File:** `server/server.zip`
- **Classification:** Binary artifact in source tree
- A prebuilt zip of the server is committed. Its contents and version are unknown without extraction. Binary artifacts in source repos complicate auditing.

#### A4 — Compiled Python bytecode committed
- **Files:** `server/__pycache__/*.pyc` (3 files: test_client, test_server, test_tls)
- Python 3.14 bytecode is committed and listed in git status as untracked. These suggest local test runs have occurred. No `.gitignore` visible at repo root that would exclude them.

#### A5 — Opus and TinyALSA built from unpinned HEAD
- **build.sh lines 79, 120:** `git clone --depth 1` without `--branch <tag>`
- Both libraries are fetched from latest HEAD on each CI run. Supply-chain risk: an upstream compromise or API-breaking commit will silently affect the build output.

#### A6 — config/audio_bridge.conf format mismatch
- The placeholder file contains a bare IP with no key prefix.
- `service.sh` (generated by build.sh) reads config using `grep '^HOST='` and `grep '^PORT='`, implying a `KEY=VALUE` format.
- The daemon's own code (audio_bridge.cpp line 1154-1159) reads the file with `fscanf(f, "%255s", hbuf)` — a bare single-token read (no keys).
- **Two incompatible config formats are in use by different components:** the daemon expects a bare IP token; service.sh expects `HOST=<ip>` KEY=VALUE format. This is a runtime configuration ambiguity.

#### A7 — server/package.json version 4.0.0 vs project v3.x
- The Node.js server declares `"version": "4.0.0"`. Every other project artifact is v3.0 or v3.1.x. No changelog or documentation explains this divergence. The Node.js server (`server.js`) may be a separately versioned rewrite.

#### A8 — README.md references Magisk as primary; CLAUDE.md references KernelSU as primary
- `README.md` line 36: "Android device with root (Magisk) and Zygisk enabled"
- `CLAUDE.md`: "Daemon runs as root via KernelSU `service.sh`"

## Phase 2 — Boot Flow Analysis

### 1. `post-fs-data.sh` Analysis

**File:** `zygisk/module/post-fs-data.sh` (4 lines)

```sh
#!/system/bin/sh
# Audio Bridge - post-fs-data.sh
# Keep this empty/minimal to never block boot
MODDIR=${0%/*}
```

**What it does:** The script is intentionally minimal. It sets `MODDIR` to the directory containing the script (line 4: `${0%/*}` strips the filename suffix from `$0`) and performs no further action. No mounts, no copies, no `chmod`, no property reads, no exits.

**Is it idempotent?** Yes, trivially. The only executable statement (`MODDIR=${0%/*}`) is a variable assignment with no side effects. Running it 0 or N times produces the same system state.

**Race conditions with KernelSU mount:** None introduced by this script. The OverlayFS module mounts performed by KernelSU's `post-fs-data` hook happen *before* `post-fs-data.sh` is executed (the module files are already overlaid into `/system` by the time this script runs). Because the script performs no mount operations itself, it cannot race with KernelSU's own mount sequencing.

**Design note (per comment at line 3):** The comment "Keep this empty/minimal to never block boot" is explicit intent. `post-fs-data` runs while the filesystem is being prepared; any blocking operation here (sleep, network, property wait) would delay the entire init sequence. Keeping it empty is the correct defensive pattern.

**Missing `customize.sh` in source tree:** `customize.sh` is not present in the checked-in source (it is generated by `build.sh`'s `build_zygisk()` function at build time). It is not a `post-fs-data` script — it is the installation customizer run by the flasher (Magisk/KernelSU) when the module zip is first flashed. It is not part of the per-boot lifecycle.

### 2. `service.sh` Full Stage Analysis

**File:** `zygisk/module/service.sh` (181 lines)
**Execution context:** `late_start service` — runs after Zygote starts, after most system services are up, but before `sys.boot_completed` is set (framework may still be initializing).

#### Stage 1 — Logging setup (lines 1-5)
```sh
MODDIR=${0%/*}
LOG=/data/local/tmp/audio_bridge_service.log
echo "$(date) Audio Bridge service.sh started" >> $LOG
```
Sets `MODDIR` and writes a timestamped entry to the log file. The log is append-only (`>>`), so repeated runs accumulate entries rather than overwriting — useful for debugging reboots, no data loss risk.

**Potential failure mode:** `/data/local/tmp` might not exist if this runs extremely early on a first-boot scenario. In practice, `/data/local/tmp` is always present by `late_start service` stage. Low risk.

#### Stage 2 — Permission grants (lines 7-20)
```sh
pm grant com.audiobridge android.permission.CALL_PHONE 2>/dev/null
pm grant com.audiobridge android.permission.ANSWER_PHONE_CALLS 2>/dev/null
pm grant com.audiobridge android.permission.READ_PHONE_STATE 2>/dev/null
pm grant com.audiobridge android.permission.READ_PRECISE_PHONE_STATE 2>/dev/null
pm grant com.audiobridge android.permission.SEND_SMS 2>/dev/null
pm grant com.audiobridge android.permission.RECEIVE_SMS 2>/dev/null
pm grant com.audiobridge android.permission.READ_SMS 2>/dev/null
pm grant com.audiobridge android.permission.POST_NOTIFICATIONS 2>/dev/null
pm grant com.audiobridge android.permission.RECORD_AUDIO 2>/dev/null
appops set com.audiobridge RECORD_AUDIO allow 2>/dev/null
appops set com.audiobridge SYSTEM_ALERT_WINDOW allow 2>/dev/null
```

**What it does:** Grants 9 runtime permissions plus 2 AppOps overrides. All calls are redirected `2>/dev/null`, so failures are silently discarded.

**Potential failure modes:**
- `pm` starts at `late_start service` but the Package Manager may not be fully ready. If `pm grant` is called before PackageManagerService accepts binder requests, it will fail silently (line 8-16 all use `2>/dev/null`).
- If `com.audiobridge` is not yet installed (first boot before the background subshell at line 94 runs `pm install`), every `pm grant` call fails silently. The grants must be re-run post-install. The background subshell does NOT re-issue `pm grant` after installation — **the granted permissions on first install depend entirely on this stage running after the app is registered, or on `pm install -r -g` (line 116) which grants all declared permissions on install.**
- `android.permission.READ_PRECISE_PHONE_STATE` (line 11) is a `privileged` permission. `pm grant` can grant it only if the package is installed in a privileged location or if the permission is allowlisted. If `com.audiobridge` is installed as a data-app (the preferred path per lines 118-122), `pm grant` for this permission will fail silently. **This is a functional gap: `READ_PRECISE_PHONE_STATE` may not be grantable to a data-app installation.**
- `CAPTURE_AUDIO_OUTPUT` is explicitly noted at line 17-19 as un-grantable via `pm grant`; it relies on the `privapp-permissions-audiobridge.xml` allowlist. But since the preferred path (lines 118-122) deliberately avoids `priv-app` to circumvent the Android 16 crash, the `privapp-permissions-audiobridge.xml` mechanism is also unavailable for data-app installs. **This means `CAPTURE_AUDIO_OUTPUT` is not grantable in the normal data-app path.** The `appops` override at line 20 (`RECORD_AUDIO allow`) attempts to compensate for `OP_RECORD_AUDIO_OUTPUT`, but AppOps and permission checks are separate layers.

#### Stage 3 — SELinux policy injection (lines 23-48)
```sh
APP_DOMAINS="priv_app system_app platform_app radio"
DAEMON_DOMAINS="ksu magisk su init"
apply_rule() {
    local RULE="$1"
    if command -v magiskpolicy >/dev/null 2>&1; then
        magiskpolicy --live "$RULE" 2>/dev/null
    elif [ -f /data/adb/ksud ]; then
        /data/adb/ksud apply-sepolicy "$RULE" 2>/dev/null
    elif command -v supolicy >/dev/null 2>&1; then
        supolicy --live "$RULE" 2>/dev/null
    fi
}
```
The `apply_rule` function probes for three policy tools in order: `magiskpolicy` (Magisk), `/data/adb/ksud` (KernelSU), `supolicy` (SuperSU). This is belt-and-suspenders — `sepolicy.rule` (generated at build time) is loaded by KernelSU/Magisk automatically; `service.sh` re-applies them live in case the auto-load missed any.

Rules applied (lines 40-44):
- For every `(APP_DOMAIN, DAEMON_DOMAIN)` pair: allow Unix stream socket `{ connectto read write getattr }` — this permits the app to connect to the daemon's `@audio_bridge` abstract socket.
- Allow `priv_app` to read/write `shell_data_file` — covers the Java-side log to `/data/local/tmp`.

**Potential failure modes:**
- Line 38: If none of the three tools is found, the `else` branch at line 47 logs a warning but does not abort. The daemon will start, but the app will be unable to connect to the socket (SELinux EACCES). Boot completes but the system is non-functional.
- `/data/adb/ksud apply-sepolicy` is not a documented KernelSU CLI subcommand (KernelSU's ksud binary uses `--allow` rules differently). **CHƯA ĐỦ BẰNG CHỨNG ĐỂ KẾT LUẬN** whether this exact invocation works on current KernelSU builds — the ksud CLI interface is not provided in this repo's source.
- All `apply_rule` calls use `2>/dev/null`. Failures are undetected except by runtime SELinux audit logs.

#### Stage 4 — Daemon launch (lines 51-91)
```sh
DAEMON_BIN=""
if [ -f "$MODDIR/files/audio-bridge" ]; then
    chmod 755 "$MODDIR/files/audio-bridge" 2>/dev/null
    DAEMON_BIN="$MODDIR/files/audio-bridge"
fi
```
Locates the daemon binary at `$MODDIR/files/audio-bridge` (line 53). The binary is `chmod 755` in-place (line 54) — necessary because the OverlayFS module mount may not preserve execute bits.

**`start_daemon()` function (lines 58-67):**
```sh
start_daemon() {
    "$DAEMON_BIN" --daemon >> $LOG 2>&1 &
    sleep 3
    if pidof audio-bridge >/dev/null 2>&1; then ...
    else echo "WARNING: Daemon failed to start" >> $LOG
    fi
}
```
Launches the daemon in the background (`&`), then `sleep 3` and checks `pidof`. The 3-second sleep is a fixed polling delay — not an event-driven check.

**Daemon start logic (lines 69-91):**
```sh
if [ -z "$DAEMON_BIN" ]; then
    echo "ERROR: audio-bridge binary not found" >> $LOG
elif ! pidof audio-bridge >/dev/null 2>&1; then
    start_daemon                                   # line 73: normal start path
else
    # Stale pidof check: wait up to 5 s
    STALE=0
    for _w in 1 2 3 4 5; do
        sleep 1
        if ! pidof audio-bridge >/dev/null 2>&1; then
            STALE=1; break
        fi
    done
    if [ "$STALE" = "1" ]; then
        start_daemon                               # line 86: stale-daemon restart
    else
        echo "Daemon already running" >> $LOG      # line 89: skip start
    fi
fi
```

**Idempotency of daemon start:** The guard at line 71 (`! pidof audio-bridge`) prevents double-launching a healthy daemon. If the daemon is already running (from a previous `service.sh` invocation or `scripts/start.sh`), the script enters the stale-check loop (lines 77-84) and waits up to 5 seconds. Only if `pidof` disappears during that window does it restart. This is **idempotent for a healthy daemon** but has a race condition: if the daemon is starting concurrently (spawned by another process), `pidof` may or may not find it within the 5-second window, potentially causing a double-start.

**Potential failure modes:**
- `pidof audio-bridge` matches any process named `audio-bridge`, not just the module's daemon. If another binary with that name exists, the guard would falsely conclude the daemon is already running (line 89) and skip the real start.
- `sleep 3` at line 61 is a fixed wait; on a heavily loaded device the daemon might not have written its PID file within 3 seconds even if it launched successfully.
- If `$MODDIR/files/audio-bridge` does not exist (artifact not copied during build — see Phase 1 finding that it is a build artifact not in source), the script logs an error and stops; the system is non-functional.

#### Stage 5 — Background subshell: APK install + FGS start (lines 94-150)
This entire block runs in a background subshell (`( ... ) &`, line 94/150).

**boot_completed wait (lines 96-99):**
```sh
for i in $(seq 1 60); do
    if [ "$(getprop sys.boot_completed)" = "1" ]; then break; fi
    sleep 2
done
sleep 3
```
Polls `sys.boot_completed` every 2 seconds for up to 120 seconds (60 × 2s), then adds 3 more seconds. Maximum wait: 123 seconds. If `boot_completed` is never set (e.g., bootloop), the loop exits after 120s and proceeds — potentially calling `pm install` during a non-ready state.

**APK install logic (lines 111-126):**
Three paths based on `pm path com.audiobridge`:
1. **Not installed (line 113):** `pm install -r -g "$MODDIR/AudioBridge.apk"` — installs fresh, grants all declared permissions (`-g`).
2. **Installed in `/system/priv-app/` (line 118):** Reinstalls from data-app path with `pm install -r -g` — documented reason: avoids Android 16 `handleBindApplication` null-deref crash with priv-app resource initialization (lines 103-110).
3. **Already data-app (line 125):** Skips install, logs "data-app, ok".

**Potential failure modes:**
- `pm install -r -g` at line 116 requires `$MODDIR/AudioBridge.apk` to exist. This is a build artifact (not in source tree). If the module was partially installed without the APK, the `[ -f "$MODDIR/AudioBridge.apk" ]` guard at line 115 silently skips installation, leaving `com.audiobridge` unregistered.
- On first boot after flash, `pm path com.audiobridge` returns empty (line 113), so `pm install` is attempted. If the APK install fails (e.g., signature mismatch, storage full), the condition at line 135 (`pidof com.audiobridge`) will be false and the fallback path at line 142 is tried.
- There is a **2-second sleep at line 117** after install, then the FGS start is attempted immediately. If the APK install takes longer (large APK, slow I/O), 2 seconds may be insufficient for `PackageManagerService` to complete optimization.

**FGS start (lines 132-149):**
```sh
FGS_OUT=$(am start-foreground-service --user 0 com.audiobridge/.AudioBridgeService 2>&1)
echo "$(date) FGS direct: $FGS_OUT" >> $LOG
sleep 4
if pidof com.audiobridge >/dev/null 2>&1; then
    exit 0
fi
# Fallback via LauncherActivity
OUT=$(am start --user 0 -n com.audiobridge/.LauncherActivity 2>&1)
sleep 4
if pidof com.audiobridge >/dev/null 2>&1; then ...
else echo "WARNING: AudioBridgeService not running after both attempts" >> $LOG
fi
```

**Primary path (line 132):** `am start-foreground-service` called as root (uid=0). The comment at lines 129-131 correctly notes that uid=0 is exempt from Android 12+ background FGS restrictions in `ActiveServices.java`.

**Fallback path (lines 141-149):** `am start LauncherActivity` — `LauncherActivity` has a translucent theme that creates a window, making the process "visible" and thus exempt from FGS background restrictions.

**Both paths use `sleep 4` (lines 134, 146) then `pidof` to detect success.** Same fixed-wait weakness as the daemon check.

**Potential failure modes:**
- If `am start-foreground-service` succeeds but `AudioBridgeService.startForeground()` is not called within 5 seconds, the system raises `ForegroundServiceDidNotStartInTimeException` and kills the service. The `pidof` check 4 seconds after the `am` call may observe the process before this timeout fires, falsely reporting success.
- The fallback `am start LauncherActivity` starts an Activity in addition to the Service. If the user sees an unexpected Activity on screen during boot, this is a UX problem for a "stealth" remote-control tool.

#### Stage 6 — Background status refresh loop (lines 152-180)
```sh
(
    WROOT="$MODDIR/webroot"
    while true; do
        P=$(cat /data/local/tmp/audio_bridge.pid 2>/dev/null | tr -d ' \t\n\r')
        H=$(grep '^HOST='  /data/local/tmp/audio_bridge.conf 2>/dev/null | cut -d= -f2-)
        PR=$(grep '^PORT=' /data/local/tmp/audio_bridge.conf 2>/dev/null | cut -d= -f2-)
        TK=$(grep '^TOKEN=' /data/local/tmp/audio_bridge.conf 2>/dev/null | cut -d= -f2-)
        ZY=$(logcat -b main -d -t 100 -s AudioBridge-Zygisk 2>/dev/null | grep -c "Connected to daemon")
        ...
        printf '{"running":...}' > "$WROOT/status.json" 2>/dev/null
        tail -n 60 /data/local/tmp/audio_bridge.log > "$WROOT/daemon.log" 2>/dev/null
        tail -n 25 /data/local/tmp/audio_bridge_service.log > "$WROOT/service.log" 2>/dev/null
        sleep 15
    done
) &
```

**What it does:** Runs indefinitely as a background process, refreshing `webroot/status.json`, `webroot/daemon.log`, and `webroot/service.log` every 15 seconds. This lets the KernelSU WebUI display current daemon state via static file reads (no exec bridge needed).

**Potential failure modes:**
- This loop **never terminates**. It runs for the lifetime of the shell process that sourced `service.sh`. If KernelSU re-executes `service.sh` on a secondary boot attempt (CHƯA ĐỦ BẰNG CHỨNG ĐỂ KẾT LUẬN on KernelSU re-exec behavior), a second loop instance would be created with no deduplication guard.
- `logcat -b main -d -t 100` at line 162 drains 100 logcat lines every 15 seconds. This is a non-trivial I/O operation that could contribute to wakelock contention on a battery-constrained device.
- The `while true; do ... sleep 15; done` loop has no exit condition. If the module is removed (uninstall.sh runs), this loop continues running until the device reboots, writing stale data to a `$WROOT` path that no longer belongs to an active module.
- Writing to `$MODDIR/webroot/status.json` with `> file` (truncate-then-write, line 169) is not atomic. A WebUI read concurrent with a write could observe a truncated/empty JSON file. No locking mechanism is present.

### 3. `BootReceiver.java` Analysis

**File:** `java/com/audiobridge/BootReceiver.java` (64 lines)

#### Intent filters (lines 46-49)
```java
if (!Intent.ACTION_BOOT_COMPLETED.equals(action)
        && !"com.audiobridge.START".equals(action)) {
    diag("ignored (unknown action)");
    return;
}
```
The receiver handles exactly two intents:
1. `android.intent.action.BOOT_COMPLETED` — fired by the system when boot is complete (i.e., `sys.boot_completed=1`).
2. `com.audiobridge.START` — custom broadcast, intended for post-install FGS start from `service.sh` (documented in the class Javadoc, lines 14-26).

#### What it starts (lines 51-62)
```java
Intent svc = new Intent(context, AudioBridgeService.class);
if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.O) {
    context.startForegroundService(svc);
} else {
    context.startService(svc);
}
```
Calls `startForegroundService()` on Android 8.0+ (API 26+), `startService()` on older. No extras are passed to the service.

#### Double-start risk with `service.sh`

There are **two independent code paths that can both start `AudioBridgeService`:**

**Path A — `service.sh` (lines 132-149):**
```
service.sh background subshell
  → waits sys.boot_completed=1
  → pm install (if needed)
  → am start-foreground-service com.audiobridge/.AudioBridgeService   [line 132]
  → fallback: am start com.audiobridge/.LauncherActivity              [line 142]
```

**Path B — `BootReceiver.onReceive()` (BootReceiver.java lines 41-62):**
```
sys.boot_completed fires
  → android.intent.action.BOOT_COMPLETED broadcast delivered to BootReceiver
  → context.startForegroundService(AudioBridgeService.class)
```

**Both paths trigger at the same event (`sys.boot_completed=1`) and both call `startForegroundService` on `AudioBridgeService`.** The Android framework deduplicates `startForegroundService` calls for the same component: if the service is already running, `onStartCommand()` is called again with a new `startId` but no second instance is created. However:

1. **Timing race on first boot (APK not yet installed):** The background subshell (Path A) must call `pm install` before starting the FGS. `BootReceiver` (Path B) fires as soon as `BOOT_COMPLETED` is broadcast. If the APK was already installed (from a prior boot), Path B fires immediately and starts `AudioBridgeService`. Then Path A's background subshell also reaches the FGS start code (line 132) and calls `am start-foreground-service` again. The service receives two `onStartCommand()` invocations within ~7 seconds (Path B + `sleep 4` + Path A). This is **not a crash** but causes redundant `onStartCommand` processing.

2. **The `com.audiobridge.START` broadcast (Path A intent, documented line 23 of BootReceiver.java):** The Javadoc says this broadcast "lets us start the FGS after systemless-module install, where `BOOT_COMPLETED` already fired." However, no code in `service.sh` sends `am broadcast com.audiobridge.START`. The receiver is registered for this action but `service.sh` never uses it — the module's FGS start goes directly through `am start-foreground-service` (line 132). The `com.audiobridge.START` path is **dead code in the current implementation.**

3. **`am start LauncherActivity` fallback (line 142):** If Path A's direct FGS start fails and it falls back to launching `LauncherActivity`, and Path B has already started the service, `LauncherActivity` would start the service a third time via its own `startForegroundService` call. Three `onStartCommand` invocations on a single boot is possible, though the service behavior for repeated calls is not analyzed in this audit.

### 4. `scripts/` Analysis

**Context:** These are manual helper scripts located in `scripts/`, separate from the KernelSU module lifecycle in `zygisk/module/`. They are NOT part of the flashed module zip (the zip packages `zygisk/module/`, not `scripts/`). They are development/maintenance tools intended for adb shell use.

#### `scripts/install.sh` (35 lines)
**Purpose:** Manual one-shot installation script. Copies the daemon binary from `/sdcard/audio-bridge` to `/data/local/tmp/`, copies Zygisk module files from `/sdcard/zygisk_module/*` to `/data/adb/modules/audio_bridge/`, and starts the daemon in the background.

**How it differs from the KernelSU module lifecycle:**
- **Binary location:** Copies daemon to `/data/local/tmp/audio-bridge` (line 18-19). The KernelSU module path uses `$MODDIR/files/audio-bridge` (service.sh line 53). These are **different paths**; `start.sh` reads from `/data/local/tmp/audio-bridge` (line 14), while `service.sh` launches from `$MODDIR/files/audio-bridge`. The two systems are **not interoperable** for daemon binary location.
- **Config format:** Line 26 writes a bare IP string (`YOUR_SERVER_IP`) to `/data/local/tmp/audio_bridge.conf`. As noted in Phase 1 Anomaly A6, `service.sh` reads `HOST=`, `PORT=`, `TOKEN=` keys from this file — the bare-IP format is incompatible with `service.sh`'s parser (lines 159-161 of service.sh).
- **No APK install:** `install.sh` does not install the APK. It only handles the native daemon binary and Zygisk module files.
- **No permission grants, no SELinux rules:** None of the `pm grant` or `apply_rule` logic from `service.sh` is present.
- **No boot persistence:** The daemon is started with `&` (line 30) but there is no systemd/init.d/service.d integration. The daemon will not restart on reboot unless the KernelSU module is also installed.

#### `scripts/start.sh` (22 lines)
**Purpose:** Starts the daemon manually (for development/testing).

**Guard condition (lines 6-12):**
```sh
if [ -f /data/local/tmp/audio_bridge.pid ]; then
    PID=$(cat /data/local/tmp/audio_bridge.pid)
    if kill -0 $PID 2>/dev/null; then
        echo "Already running (PID: $PID)"
        exit 0
    fi
fi
```
Checks for the PID file and verifies liveness with `kill -0`. This guard is **not equivalent to `pidof`** (used in `service.sh`): it only prevents double-start if the daemon wrote a PID file. If the daemon did not write `/data/local/tmp/audio_bridge.pid` (e.g., crashed before writing it), this guard does not prevent a re-launch.

**Binary path:** `/data/local/tmp/audio-bridge` (line 14) — the manual install path, NOT the module path.

**How it differs from `service.sh`:** No permission grants, no SELinux rules, no APK install, no boot_completed wait, no WebUI status loop. It is a raw process launcher only.

#### `scripts/stop.sh` (24 lines)
**Purpose:** Stops the daemon using the PID file, with fallback to `pkill -f audio-bridge`.

**PID-file path (line 6):** `/data/local/tmp/audio_bridge.pid` — same manual-path convention as `start.sh`.

**SIGTERM → SIGKILL escalation (lines 9-13):**
```sh
kill $PID
sleep 1
if kill -0 $PID 2>/dev/null; then
    kill -9 $PID
fi
```
Sends SIGTERM first, waits 1 second, then SIGKILL if the process is still alive.

**Anomaly:** Line 25: `rm -f /data/local/tmp/audio_bridge.sock` — removes the Unix socket file. The daemon uses an **abstract** Unix socket (`@audio_bridge`, starting with `\0`), which does not appear as a file in the filesystem. This `rm` command targets a **named socket file** at `/data/local/tmp/audio_bridge.sock`, not the abstract socket. If the daemon creates both a named socket and an abstract socket (CHƯA ĐỦ BẰNG CHỨNG ĐỂ KẾT LUẬN from `service.sh` alone — would require reading `audio_bridge.cpp`), this cleanup is valid; otherwise it is a no-op or removes an unrelated file.

**How it differs from `service.sh`:** `service.sh` does not have a stop path — it only starts the daemon. `stop.sh` is the only script providing daemon termination via PID file. The KernelSU module system relies on device reboot to stop the daemon between installs; `uninstall.sh` uses `pidof`+`kill` directly (not `stop.sh`).

### 5. Boot Sequence Diagram

```
Android Boot
│
├─ [init: early-init stage]
│   └─ KernelSU kernel driver initializes; no user scripts yet
│
├─ [init: post-fs-data stage]
│   ├─ KernelSU overlays /system with module OverlayFS mounts
│   │   (module files from /data/adb/modules/audio_bridge/ become visible)
│   └─ EXECUTES: zygisk/module/post-fs-data.sh
│       └─ Sets MODDIR variable; exits immediately (intentionally empty)
│           → NO blocking, NO mount, NO file copy
│
├─ [init: late_start service stage]  ← runs after Zygote starts
│   └─ EXECUTES: zygisk/module/service.sh (foreground, blocking until line 180)
│       │
│       ├─ [STAGE 2] pm grant 9 permissions (lines 8-16) — may silently fail
│       ├─ [STAGE 3] Apply SELinux rules via magiskpolicy/ksud/supolicy (lines 38-48)
│       ├─ [STAGE 4] chmod + launch $MODDIR/files/audio-bridge --daemon (line 60)
│       │   └─ Daemon runs: TCP client to port 59100, Unix socket @audio_bridge,
│       │       SHM ring buffer for audio frames, Opus encode/decode
│       ├─ [STAGE 5 - background subshell] (lines 94-150) &
│       │   ├─ Poll sys.boot_completed=1 every 2s (up to 120s)
│       │   ├─ pm install -r -g AudioBridge.apk (if not data-app)
```

### 6. Anomalies and Issues Found

#### B1 — Missing `boot-completed` module lifecycle script
**Severity:** INFORMATIONAL

The KernelSU/Magisk module specification supports an optional `boot-completed` (or `boot_completed`) script hook that executes after `sys.boot_completed=1` is set. **No such script exists in the module** (`zygisk/module/` only contains `post-fs-data.sh`, `service.sh`, `uninstall.sh`, `customize.sh` — the last two are generated). The post-`boot_completed` work (APK install, FGS start) is handled by a background subshell inside `service.sh` (lines 94-150), not a dedicated `boot-completed` hook. This is a valid alternative pattern; the KernelSU `boot-completed` hook would be cleaner but is not required.

#### B2 — Double-start risk: BootReceiver + service.sh both start AudioBridgeService
**Severity:** MEDIUM
**Evidence:**
- `service.sh` line 132: `am start-foreground-service --user 0 com.audiobridge/.AudioBridgeService`
- `BootReceiver.java` line 54: `context.startForegroundService(svc)` triggered by `BOOT_COMPLETED`

Both paths fire when `sys.boot_completed=1`. The Android framework will deliver `BOOT_COMPLETED` to `BootReceiver` (Path B) immediately, while `service.sh`'s background subshell (Path A) takes an additional `sleep 3` (line 100) before calling `am start-foreground-service`. On a normal boot (APK already installed), both calls reach `AudioBridgeService` within approximately 3-7 seconds of each other, causing two `onStartCommand()` invocations. The service is not double-instantiated, but the `startId` counter increments, which could affect `stopSelf(startId)` calls inside the service.

#### B3 — `com.audiobridge.START` broadcast registered but never sent
**Severity:** LOW
**Evidence:**
- `BootReceiver.java` lines 14-26 (Javadoc): "lets us start the FGS after systemless-module install, where BOOT_COMPLETED already fired"
- `BootReceiver.java` lines 46-49: `"com.audiobridge.START".equals(action)` check present
- `service.sh` lines 94-150: FGS start uses `am start-foreground-service` directly; no `am broadcast com.audiobridge.START` anywhere in the script

The `com.audiobridge.START` broadcast receiver path is implemented in Java but the trigger (broadcast send) is absent from `service.sh`. The intent was apparently to use this as a post-install FGS trigger to avoid the `BOOT_COMPLETED` timing issue — but the implementation fell back to the direct `am start-foreground-service` approach instead.

#### B4 — Status refresh loop non-atomic write to `status.json`
**Severity:** LOW
**Evidence:** `service.sh` line 169: `printf '...' > "$WROOT/status.json"`

The `>` redirect truncates the file before writing. If the KernelSU WebUI reads `status.json` between the truncation and the write completion, it observes an empty file. The WebUI's `fetch(status.json)` then receives empty content, which will cause a JSON parse error in `app.js`. No locking (`flock`, temp-file-then-rename) is used. Mitigation: the 15-second write interval makes the collision window narrow but non-zero.

#### B5 — `start.sh` guard uses PID file, `service.sh` uses `pidof` — inconsistent dedup
**Severity:** LOW
**Evidence:**
- `scripts/start.sh` lines 6-12: checks `/data/local/tmp/audio_bridge.pid`
- `zygisk/module/service.sh` lines 71, 80: uses `pidof audio-bridge`

If the daemon is started via `service.sh` (using `pidof`-based guard) and then `start.sh` is run manually, `start.sh` reads the PID file. If the daemon wrote a PID file, `start.sh` correctly avoids double-start. But if `service.sh` launched the daemon and the daemon failed to write the PID file (or wrote it to a different path), `start.sh`'s PID check finds no file, falls through the guard, and launches a second daemon instance.

#### B6 — `install.sh` config format incompatible with `service.sh` parser
**Severity:** MEDIUM (pre-existing, also noted as Phase 1 Anomaly A6)
**Evidence:**
- `scripts/install.sh` line 26: `echo "YOUR_SERVER_IP" > /data/local/tmp/audio_bridge.conf`
- `zygisk/module/service.sh` lines 159-161: `grep '^HOST='`, `grep '^PORT='`, `grep '^TOKEN='`

If a developer uses `install.sh` to set up the config file, the `service.sh` status loop will not be able to parse `HOST`, `PORT`, or `TOKEN` from the bare-IP format. `status.json` will report empty `host`/`port`/`token` fields. The daemon itself reads the bare IP using `fscanf(f, "%255s", ...)` — compatible with the `install.sh` format. This is a persistent format mismatch between the manual path and the KernelSU module path.

#### B7 — `stop.sh` removes named socket file; daemon uses abstract socket
**Severity:** LOW
**Evidence:**
- `scripts/stop.sh` line 25: `rm -f /data/local/tmp/audio_bridge.sock`
- `CLAUDE.md`: "Java ↔ Daemon IPC: abstract Unix socket `@audio_bridge`"

Abstract Unix sockets (prefixed with `\0`) do not create filesystem entries and cannot be removed with `rm`. The `rm` call is either a no-op (if no named socket file exists at that path) or removes an unrelated file. The actual socket cleanup happens automatically when the daemon process exits.

#### B8 — SELinux `ksud apply-sepolicy` — unverified CLI interface
**Severity:** MEDIUM
**Evidence:** `service.sh` line 34: `/data/adb/ksud apply-sepolicy "$RULE" 2>/dev/null`

KernelSU's documented `ksud` CLI does not include an `apply-sepolicy` subcommand in publicly available documentation. The correct KernelSU mechanism for live policy patching is `ksud module sepolicy` or relying on the `sepolicy.rule` file auto-loaded at boot. If `ksud apply-sepolicy` is not a valid subcommand, this line fails silently (due to `2>/dev/null`) and SELinux rules are not applied on KernelSU devices that lack `magiskpolicy`. This leaves the daemon unable to receive socket connections from app processes. **CHƯA ĐỦ BẰNG CHỨNG ĐỂ KẾT LUẬN** on the exact ksud CLI interface without access to the ksud binary or its help output.

#### B9 — Daemon stale-check window allows double-start on service.sh re-run
**Severity:** LOW
**Evidence:** `service.sh` lines 77-90

The stale check waits up to 5 seconds for `pidof` to disappear. If `service.sh` is re-executed while the daemon is healthy (e.g., by a module manager action), it enters the stale-check loop. If another process kills the daemon during those 5 seconds (coincidental timing), `STALE=1` is set and `start_daemon` is called while the original daemon is still in its shutdown sequence. A brief window exists where two daemon instances could be initializing simultaneously before the first fully exits. Both would attempt to `bind()` the same abstract socket — the second `bind()` would fail with `EADDRINUSE`. The second daemon instance would likely exit immediately (CHƯA ĐỦ BẰNG CHỨNG ĐỂ KẾT LUẬN without reading `audio_bridge.cpp` error handling), but the log entry at line 86 ("Stale daemon was dying; restarting") could be misleading.

#### `service.sh`

**Source:** `zygisk/module/service.sh` (181 lines, checked-in); build-generated version `build.sh` lines 592–776.

**KernelSU lifecycle stage:** `late_start service` — runs as root after Zygote starts and most system services are up, but before `sys.boot_completed` is set.

**What it does (summary):**
1. Sets `MODDIR`, initializes log file (lines 1–5)
2. Grants 9+ runtime permissions via `pm grant` (lines 8–16 committed; lines 600–610 build-generated)
3. Applies SELinux rules via `magiskpolicy`/`ksud`/`supolicy` (lines 23–48 committed; lines 613–644 build-generated)
4. Locates and launches the daemon binary (lines 50–91)
5. Background subshell: waits for `boot_completed`, installs APK, starts FGS (lines 93–150)
6. Background status refresh loop: writes `webroot/status.json` every 15 seconds indefinitely (lines 152–180)

**Is it idempotent?**

The daemon start is conditionally idempotent: the guard at line 71 (`! pidof audio-bridge`) prevents double-launch if the daemon is healthy. The APK install at line 116 uses `pm install -r` (replace/upgrade) — safe to run again but generates duplicate log entries. The `pm grant` calls at lines 8–16 are idempotent (granting an already-granted permission is a no-op). The SELinux `apply_rule` calls are idempotent (adding already-present rules is a no-op for `magiskpolicy --live`). The status loop (lines 155–180) creates a new background process on every invocation — **not idempotent**: if `service.sh` is executed twice (e.g., by a module manager action), two perpetual status-refresh loops will run simultaneously.

**Critical difference between committed and build-generated `service.sh`:**

The `ksud` invocation for live SELinux policy differs between the two versions:

| Version | Line | ksud command |
|---------|------|-------------|
| Committed (`zygisk/module/service.sh`) | line 33 | `/data/adb/ksud apply-sepolicy "$RULE"` |
| Build-generated (`build.sh`) | line 623 | `/data/adb/ksud sepolicy patch "$RULE"` |

The build-generated version (`ksud sepolicy patch`) is the documented KernelSU CLI interface for live policy application. The committed version (`ksud apply-sepolicy`) uses a non-existent subcommand (consistent with the B8 anomaly identified in Phase 2). Since the build-generated version overwrites the committed one before zipping, the **flashed module uses the correct `ksud sepolicy patch` form** — but the checked-in source file contains the incorrect form.

**Additional difference in build-generated service.sh:**
- The SELinux rule application block is backgrounded in the build-generated version (inside a `( ... ) &` subshell, build.sh lines 628–644), while the committed version executes it inline (lines 38–48 of service.sh). The background form means `service.sh` does not block waiting for policy tool invocations, which is better practice.
- The build-generated version also grants `android.permission.READ_CALL_LOG` (build.sh line 604) which is absent from the committed version.

**KernelSU guideline compliance:**
- Uses `#!/system/bin/sh`. COMPLIANT.
- The spec discourages long-running operations in `service.sh` itself (as opposed to backgrounding them). The daemon launch includes a `sleep 3` (line 61) and the stale-check loop can run for up to 5 seconds (lines 78–84) inline — these block `service.sh` for up to 8 seconds before it reaches the background subshells. This is a minor guideline concern but not a hard violation.
- The status refresh loop (`while true; do ... sleep 15; done`) runs indefinitely with no exit condition. The KernelSU spec does not explicitly prohibit this, but it is unusual and wastes resources. LOW concern.

**Source:** `zygisk/module/uninstall.sh` (59 lines, checked-in); build-generated version `build.sh` lines 794–850.

**KernelSU lifecycle stage:** `uninstall` — runs as root during module removal, triggered by KernelSU Manager when the user removes the module. The KernelSU spec states this runs at the `post-fs-data` stage (early boot, before Android framework starts).

**What it does:**

### 5. Deviations from KernelSU Spec

The KernelSU Module Guide defines the following requirements. Each deviation is listed with what the spec requires, what the module does, and severity.

#### C1 — `META-INF/` tree absent from module zip

|---|---|
| **Spec requires** | Module zips must contain `META-INF/com/google/android/update-binary` and `META-INF/com/google/android/updater-script`. `update-binary` is the installer script run by TWRP/flasher; `updater-script` is typically empty or a comment. #### C2 — Committed `module.prop` is stale and inconsistent with build output

| | Detail |
|---|---|
| **Spec requires** | `module.prop` in the flashed zip must be accurate and consistent with `update.json` `versionCode`. |
| **Module does** | The committed `module.prop` has `version=v3.0`, `versionCode=300`, and is missing `minKernelSU` and `updateJson`. The build-generated version (the actual flashed file) has `version=v3.1.93`, `versionCode=93`, and includes both optional fields. |
| **Severity** | **MEDIUM** — The committed file is never flashed (overwritten at build time), so there is no runtime impact. However, any developer inspecting the source `module.prop` to understand the deployed state will see incorrect information. The `versionCode=300` vs `versionCode=93` discrepancy is particularly confusing. |

#### C3 — `ksud apply-sepolicy` in committed `service.sh` is not a valid KernelSU CLI subcommand

| | Detail |
|---|---|
| **Spec requires** | Live SELinux policy application on KernelSU uses `ksud sepolicy patch <rule>` or relies on the `sepolicy.rule` file auto-loaded at boot. |
| **Module does** | Committed `service.sh` line 33: `/data/adb/ksud apply-sepolicy "$RULE"`. Build-generated `service.sh` (build.sh line 623): `/data/adb/ksud sepolicy patch "$RULE"`. |
| **Severity** | **MEDIUM** — The committed file would not work correctly on KernelSU devices if used. However, since build.sh overwrites it before zip assembly, the flashed module uses the correct form. The committed file is misleading but not functionally deployed. (This finding was also identified in Phase 2 as anomaly B8, confirmed here from the build.sh source of truth.) |

#### C4 — No `system/` overlay (intentional but undocumented)

| | Detail |
|---|---|
| **Spec requires** | OverlayFS modules can optionally include a `system/` directory whose contents are overlaid onto `/system` at `post-fs-data` stage. This is the standard mechanism for installing APKs as system/priv-app. |
| **Module does** | No `system/` directory exists. The APK is delivered via `pm install -r -g` from `service.sh` instead. `customize.sh` removes any residual `system/` overlay from prior builds. |
| **Severity** | **INFORMATIONAL** — `system/` is optional per spec. The design decision is documented in build.sh comments (lines 102–110: Android 16 priv-app crash avoidance). The absence of `system/` means the APK installs as a data-app, not a true system app — with implications for privileged permission grants (see Phase 2 anomaly B2 and Stage 2 analysis). |

#### C5 — No `system.prop` file

| | Detail |
|---|---|
| **Spec requires** | Modules may optionally include `system.prop` at the module root; KernelSU will set these properties at `post-fs-data` stage via `resetprop`. |
| **Module does** | No `system.prop` file is generated or shipped. |
| **Severity** | **INFORMATIONAL** — `system.prop` is optional. The module does not require custom system properties at the kernel/init level. No deviation from a hard requirement. |

#### C6 — `service.sh` status refresh loop never terminates

| | Detail |
|---|---|
| **Spec requires** | The KernelSU spec does not explicitly prohibit non-terminating background processes from `service.sh`, but the spirit of the module lifecycle is that `service.sh` should perform setup work and exit, not maintain perpetual background processes independent of module lifetime. |
| **Module does** | `service.sh` lines 155–180: a `while true; do ... sleep 15; done` loop runs in a background subshell indefinitely. It has no connection to module removal or daemon lifecycle — it continues running after module uninstall until reboot. |
| **Severity** | **LOW** — No hard spec violation; `service.sh` is not required to exit. The perpetual loop consumes resources (logcat drain every 15 seconds) and survives module uninstall. |

#### C7 — `versionCode` derived from commit count, not semantic versioning

| | Detail |
|---|---|
| **Spec requires** | `versionCode` must be an integer that increments with each new release. The spec does not mandate a specific derivation method. |
| **Module does** | `versionCode = git rev-list --count HEAD` (build.sh line 530). This is the total commit count on the branch, not a manually managed integer. |
| **Severity** | **INFORMATIONAL** — Technically compliant (always an incrementing integer for a linear history). However, this means any commit — including `[skip ci]` CI housekeeping commits (e.g., `update.json` push-back) — increments `versionCode`. A commit-count `versionCode` also resets to 1 if the branch is rewritten, and diverges from `update.json` if commits are added without a release. |

#### C8 — `uninstall.sh` removes abstract socket path as filesystem file

| | Detail |
|---|---|
| **Spec requires** | The spec does not address socket cleanup specifically. |
| **Module does** | `zygisk/module/uninstall.sh` line 24: `rm -f /data/local/tmp/audio_bridge.sock`. The daemon uses abstract Unix socket `@audio_bridge` (per CLAUDE.md) which has no filesystem entry. |
| **Severity** | **LOW** — The `rm` is a no-op for the abstract socket. If no other process created a named socket at that path, this command has no effect. Not a spec violation but indicates a misunderstanding of abstract vs. named Unix sockets. (Also identified in Phase 2 as anomaly B7.) |

| Finding | ID | Severity |

**Most significant finding:** The module zip lacks `META-INF/com/google/android/update-binary` (C1), which is the standard KernelSU/Magisk module installer entry point. Whether this causes flash failure depends on the KernelSU Manager version — newer versions may synthesize the wrapper internally, but older versions and TWRP recovery require it. This should be verified against the target KernelSU Manager version.

**Committed-vs-built discrepancy pattern:** A systemic issue across Phase 3 is that the committed source files (`module.prop`, `service.sh`, `post-fs-data.sh`, `uninstall.sh`) are **all overwritten at build time** by `build.sh` heredocs. The checked-in versions are stale drafts that do not represent what is actually flashed. This creates an ongoing source-of-truth confusion for anyone reading the repo without running the build.
